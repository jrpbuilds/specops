# SpecOps v0.17.0 — Deterministic Four-Stage Orchestration

> Status: implementation-ready architecture plan. This document records the
> repository investigation and the decisions for Luna to decompose into
> implementation phases. It does not represent implemented behavior.

## 1. Executive conclusion

### Confirmed conclusion

The v0.17.0 redesign is justified. The current architecture contains useful
deterministic primitives—locking, revision checks, dispatch identities, writer
guards, artifact hashing, evidence capture, OpenSpec validation, and
configurable model routing—but they are wrapped in an artifact-driven scheduler
that makes the model controller translate several internal protocols correctly
before those guarantees apply.

The recommended architecture is:

```text
ASSESS → PLAN → BUILD → VERIFY → COMPLETE
                         ↑       |
                         └ REPAIR┘
```

Key decisions:

- Keep `Lean`, `Standard`, and `Full`; renaming Lean to Simple would add
  compatibility churn without improving behavior.
- Make the TypeScript plugin authoritative for assessment dispatch, child-agent
  invocation, validation, state transitions, retries, repair scheduling, and
  finalization.
- Use OpenCode's v2 session API to launch child agents directly. Remove native
  `task` translation from the model controller.
- Replace artifact scheduler phases with four capability stages. Artifacts
  become typed stage outputs.
- Make Lean's normal path exactly four primary dispatches: assessment,
  planning, implementation, verification.
- Use specialists only from persisted deterministic triggers.
- Replace HTML control markers with capability-specific, versioned worker
  envelopes validated before any authoritative state mutation.
- Allow one explicit schema-correction attempt per dispatch. JSON Schema is a
  validation mechanism, not a guarantee that a model will respond correctly.
- Add explicit implementation epochs, finding states, repair tasks, transition
  reasons, and small tier-aware budgets.
- Reject active v0.16 state rather than attempting an unsafe semantic
  migration. Ship one canonical v0.17 engine.
- Keep OpenSpec, the full agent/model catalogue, automatic and interactive
  operation, evidence-backed verification, repository mutation guards,
  cancellation, and crash recovery.

This makes SpecOps materially different from ordinary OpenCode Plan/Build mode
through deterministic risk routing, specialist activation, validation evidence,
finding-to-repair tracking, replayable state, and a complete explanation
trace—without imposing those costs on simple work.

### Unresolved questions

No product decision remains blocking. One implementation-time compatibility
check is required: run integration tests against the exact locked OpenCode
1.18.10 runtime after `npm ci`, because the checked-in lockfile targets 1.18.10
while the inspected local `node_modules` installation was stale at 1.16.2.

## 2. Current architecture map

### Command through run creation

1. `/specops` and `/specops-auto` in `src/commands.ts` select the primary
   controller prompts from `src/prompts.generated.ts`.
2. The controller is instructed to invoke the native OpenCode `task` tool with
   the `specops-assessor` agent and the exact user goal.
3. The assessor returns strict-looking but still model-generated JSON.
4. The controller reconstructs a `specops_start_run` call containing the goal,
   assessment serialized as a string, requested tier, and mode.
5. `startRun()` in `src/workflow/engine.ts` parses the assessment through
   `parseAssessment()`, evaluates routing through `requirementsFor()`, calls
   `uniqueChangeName()` in `src/openspec.ts`, checks the worktree, invokes
   OpenSpec change creation, enters `withRunLock()` in `src/state/store.ts`, and
   constructs `RunState` version 6 and its baseline, routing, exploration,
   artifact, context, evidence, and progress records.

OpenSpec creation currently occurs before the authoritative run-state
transaction, so startup is not atomic.

### Dispatch and completion

1. The controller calls `specops_next_action`.
2. `issueDirective()` locks the run, rejects a second live issued dispatch,
   refreshes implementation bindings, and calls `nextDirective()`/
   `nextAction()`.
3. `nextAction()` in `src/workflow/scheduler.ts` evaluates a large ordered
   decision tree: pending frontier episode, repair, replay/resumption,
   exploration, proposal/planning bundle, design, tasks, every selected
   specialist consultation, implementation, verification, correctness
   judgment, compliance judgment, general-risk review, specialist reviews,
   refuter/review ledger, and finalization.
4. The resulting `WorkflowAction` contains fields such as `id`, `agent`,
   `capability`, `purpose`, `mode`, `artifact`, and `prompt`.
5. The controller converts that object to OpenCode's different native task
   schema: `agent` becomes `subagent_type`, it invents `description`, passes
   `prompt`, and later extracts a worker result from OpenCode's task wrapper.
6. The controller sends the reconstructed output to
   `specops_complete_action`.
7. `completeAction()` in `src/workflow/engine.ts` validates the issued dispatch,
   applies writer guards, parses free-form output and embedded control markers,
   and then updates artifacts, questions, frontier state, findings, repairs,
   checkpoints, evidence, and progress.

### Repair and review

- `src/workflow/reviews.ts` normalizes review submissions and produces
  findings.
- A model-generated refuter/review-ledger episode can accept, dismiss, or
  escalate findings.
- Accepted blockers become `RepairTask` records.
- A pending repair outranks normal scheduling.
- A successful repair invalidates affected artifact/evidence graph nodes and
  returns the run to verification and review.
- There is no explicit monotonic implementation epoch;
  `implementationDiffHash` and a broader `assuranceEpoch` hash are used as
  proxies.

### Finalization and archive

- `finalizeRun()` checks that the scheduler has no remaining action, repair
  tasks are resolved, required artifacts are valid, validation evidence exists,
  and OpenSpec status and strict validation pass.
- It writes a final receipt and successful outcome.
- `/specops-archive` creates a confirmation flow. The controller asks the user
  through OpenCode, reconstructs the response, and calls the archive
  confirmation tool. OpenSpec then archives the change and merges specs where
  applicable.

### Current controller-facing protocol

`src/protocol.ts` and `src/orchestrator.ts` expose 19 identifiers or operations,
including start, next action, completion, recovery, questions, checkpoints,
context, validation, status, cancellation, finalization, archival, onboarding,
doctoring, and generic OpenSpec access.

### Model translation and reconstruction boundaries

A model currently has to translate or reconstruct protocol at all of these
points:

- User goal → assessor task payload.
- Assessor output → `specops_start_run` assessment string.
- `WorkflowAction` → native OpenCode task input.
- Native OpenCode task wrapper → bare worker output.
- Verifier instructions → `specops_run_validation` arguments.
- Worker HTML control marker → question, escalation, or frontier behavior.
- Native question answer → one of the question/checkpoint/archive tools.
- Tool errors → a guessed recovery, retry, resumption, or altered input.
- Archive prompt result → archive confirmation payload.

The inspected OpenCode 1.18.10 native task schema is:

```ts
{
  description: string;
  prompt: string;
  subagent_type: string;
  task_id?: string;
  command?: string;
}
```

Its result is wrapped in `<task>`/`<task_result>` text, whereas SpecOps tells the
controller to submit the worker output unmodified. This is a direct protocol
mismatch.

### Free-form output that affects control flow

Free-form or model-authored data currently influences progression through:

- assessment JSON;
- question, escalation, and frontier HTML markers;
- judgment verdicts and findings;
- specialist findings;
- the refuter ledger;
- frontier dispositions;
- planning JSON and Markdown;
- verification Markdown;
- implementer prose combined with observed repository changes;
- summaries used by fingerprints and stall logic;
- human feedback interpreted and routed by the controller.

### Existing deterministic guarantees worth retaining

The following are real backend guarantees once a valid request reaches them:

- exclusive run and archive locks;
- revision-based optimistic concurrency;
- one current issued dispatch;
- dispatch identity checks and once-only completion;
- artifact path confinement;
- Git HEAD, stash, and protected-tree writer guards;
- no-shell validation execution with cwd restrictions, timeouts, bounded
  output, and redaction;
- hashes for artifacts, policy, diff, evidence, and answers;
- OpenSpec strict validation;
- rejection of unsupported state versions;
- explicit agent permissions and configurable model manifests.

They do not prevent a controller from supplying the wrong schema, changing the
goal before startup, stripping or retaining the wrong task wrapper, or
improvising after an internal error.

## 4. Complexity inventory

### Accidental complexity to remove

- Artifact names acting as scheduler phases.
- A 1,189-line ordered `nextAction()` decision tree.
- Separate normal, resume, recovery, and frontier action construction.
- Mandatory correctness, compliance, general-risk, specialist-review, and
  refuter dispatches for routine work.
- Separate tools for workflow actions that can be internal state transitions.
- HTML comments embedded in otherwise human-readable output.
- Multiple authoritative or semi-authoritative state sidecars.
- A model-supplied tier suggestion that routing ignores.
- Model-driven selection of frontier behavior.
- Controller instructions that compensate for backend defects.
- Broad loop guards that permit many redundant calls before stopping.

### Duplicated contracts

The same concepts are represented independently in:

- OpenSpec's identifier validator, SpecOps tool schemas, store schemas, and slug
  generation.
- TypeScript enums, parser sets, capability registries, prompt text,
  documentation, and tests.
- `Assessment`, its manual parser, assessor prompt, routing logic, and fixtures.
- Finding types, parsing constants, generated worker contracts, and OpenSpec
  templates.
- Protocol IDs, Zod tool schemas, command templates, controller prompts, and
  documentation.
- Artifact requirements in routing, scheduler order, graph definitions, three
  YAML schema variants, and workflow docs.
- `RunState` TypeScript types, shallow read validation, sidecar formats,
  receipts, and test fixtures.
- Normal dispatch builders and replay/resume builders.
- `schemas/` and `openspec/schemas/`.

Canonical Zod schemas and generated JSON Schema should replace manual
repetitions. Prompts should receive schemas from the runtime instead of
embedding copied wire formats.

### Normal redispatch routes today

The same capability can run again through ordinary scheduler progression,
failed-dispatch replacement, `resumeAction()`, frontier resumption, checkpoint
regeneration, invalidation after repair, verification or review retry, stale
assurance epoch detection, escalation-added capability, and controller retries
after tool errors.

All should converge on one canonical transition and dispatch builder.

### Why current review loops survive stall detection

- The implementation epoch is not explicit.
- Verification output is included in assurance identity, so new prose can make
  the epoch appear new without code changes.
- The same reviewer can be dispatched through normal and replay routes.
- Repairs may not be scheduled until the full review/refuter chain completes.
- Checkpoint regeneration can create a new checkpoint identity.
- The consultation guard tolerates up to 12 consultations.
- Malformed non-assurance output has no global one-correction limit.
- Review work can continue against an unchanged diff before an actionable
  finding is converted to repair.

### Valuable abstractions to retain

- OpenSpec as the specification and archive system.
- The specialist and multi-model catalogue.
- Capability/purpose distinction.
- Risk facets and deterministic thresholds.
- Repository writer guards.
- Locked, revisioned persistence.
- Evidence references and command evidence.
- Artifact dependency knowledge, refactored into versioned evidence
  dependencies.
- Automatic and interactive modes.
- Safe cancellation and archive confirmation.

## 5. Target architecture

### Stage and transition model

```ts
type RunStage =
  | "assess"
  | "plan"
  | "build"
  | "verify"
  | "repair"
  | "complete"
  | "blocked"
  | "cancelled";

type Transition =
  | { type: "dispatch"; request: WorkerRequest; reason: TransitionReason }
  | { type: "dispatch-batch"; requests: WorkerRequest[]; reason: TransitionReason }
  | { type: "move"; from: RunStage; to: RunStage; reason: TransitionReason }
  | { type: "pause"; pause: PauseRequest; reason: TransitionReason }
  | { type: "finish"; outcome: RunOutcome; reason: TransitionReason }
  | { type: "block"; error: RunError; reason: TransitionReason };

type TransitionReason = {
  code: ReasonCode;
  triggerIds: string[];
  evidenceIds: string[];
};
```

`selectTransition(state, repositorySnapshot)` must be pure. Given the same
validated state and snapshot, it returns the same transition and deterministic
dispatch identities.

Every accepted transition records sequence, before and after state hashes,
stage and implementation epoch, closed reason code, trigger and evidence IDs,
consumed budgets, and issued dispatch IDs. Timestamps are audit metadata and do
not participate in transition selection.

### Tier behavior

| Tier | Default stages | Conditional episodes |
|---|---|---|
| Lean | Assessor, planner, implementer, verifier | One repair/reverify cycle if needed; no specialists or frontier by default |
| Standard | Same four stages, with proposal/spec/task outputs | Risk-triggered Plan consultations, Verify reviews, up to two repairs, one adjudication/frontier episode |
| Full | Same visible stages, richer Plan and Verify outputs | Bounded exploration, design, specialists, independent judges, adjudication, and frontier based on triggers or policy |

Routing rules:

- Full for breaking changes, migrations, infrastructure scope, configured size
  thresholds, forced-full facets, or **low requirements/design confidence**.
- Standard for features, refactors, compatible requirement changes, material
  risks, medium requirements/design confidence, or work over Lean limits.
- Lean for small restorative, documentation, test, or configuration work with
  no material risk and **high requirements/design confidence**.
- Other confidence dimensions influence specialist episodes rather than
  automatically inflating the whole tier.

The old field `uncertainty` becomes `confidence`. If it had remained named
uncertainty, the suspicious comparison would indeed need to be `"high"`;
renaming removes that semantic trap.

### Immutable semantic input and change identity

```ts
type SemanticInput = {
  originalGoal: string;
  goalHash: string;
  requestedTier?: "lean" | "standard" | "full";
  mode: "automatic" | "interactive";
  constraints: SourceBoundConstraint[];
  references: SourceBoundReference[];
};

type DerivedIdentity = {
  changeId: string;
  displaySummary: string;
};
```

Rules:

- `originalGoal` is stored and dispatched byte-for-byte.
- Constraints and references derived by a model must cite exact spans in the
  original goal; unmatched derivations are rejected.
- Display summaries and identifiers are never substituted for the semantic
  goal.
- The controller cannot submit an assessment or rewritten goal to recover an
  internal error.

Change-name generation:

1. Unicode NFKD normalization and removal of combining marks.
2. Lowercase.
3. Replace invalid runs with `-`.
4. Collapse and trim separators.
5. Ensure the identifier starts with a letter; use `change` or a `change-`
   prefix when required.
6. Reserve six characters for a collision suffix; truncate the base to 42
   characters.
7. Trim separators again.
8. Validate against OpenSpec's exact rule and 48-character limit.
9. Under a repository-wide start lock, inspect active names and staged
   reservations.
10. Select the base or the smallest available suffix from `-2` through
    `-99999`.
11. Append, trim if applicable, and revalidate.
12. Invoke OpenSpec only after all invariants pass.

### Atomic startup

Add a repository-level start transaction:

- Derive `startRequestId` from the OpenCode session/message identity and the
  immutable goal hash.
- Acquire the start lock.
- Return the existing run if that same request was already published.
- Reserve the change ID.
- Create a temporary OpenSpec project under
  `openspec/.specops-staging/<startRequestId>/`, using the repository's OpenSpec
  configuration and specs as read-only inputs.
- Run OpenSpec change creation in the staging project.
- Construct and fully validate the v7 run state, initial trace, and OpenSpec
  files in staging.
- Publish by same-filesystem rename to `openspec/changes/<changeId>`.
- Remove the reservation.
- On restart, reconcile abandoned staging directories; they are never
  considered authoritative runs.

A failure before rename leaves no authoritative run. A lost response after
rename is resolved through `startRequestId`.

### Worker request and result contracts

```ts
type WorkerRequest<R extends ResultKind = ResultKind> = {
  schemaVersion: 1;
  runId: string;
  changeId: string;
  dispatchId: string;
  stage: RunStage;
  capability: Capability;
  purpose: Purpose;
  resultKind: R;
  triggerIds: string[];
  authority: WorkerAuthority;
  semanticInput: SemanticInput;
  assessment: Assessment;
  artifacts: ArtifactInput[];
  validations: ValidationInput[];
  repository: RepositoryBinding;
};

type WorkerEnvelope<R> =
  | {
      schemaVersion: 1;
      dispatchId: string;
      status: "completed";
      result: R;
      evidence: EvidenceRef[];
      summary: string;
      control: { type: "none" };
    }
  | {
      schemaVersion: 1;
      dispatchId: string;
      status: "needs-input";
      result?: Partial<R>;
      evidence: EvidenceRef[];
      summary: string;
      control: { type: "questions"; questions: WorkerQuestion[] };
    }
  | {
      schemaVersion: 1;
      dispatchId: string;
      status: "escalated";
      result?: Partial<R>;
      evidence: EvidenceRef[];
      summary: string;
      control: { type: "escalation"; claim: EscalationClaim };
    }
  | {
      schemaVersion: 1;
      dispatchId: string;
      status: "blocked";
      evidence: EvidenceRef[];
      summary: string;
      control: { type: "blocker"; reason: BlockReason };
    };
```

Additional rules:

- Results are capability-specific discriminated unions, not an untyped
  `result: unknown`.
- Large Markdown proposal/design/spec/task content remains an inline bounded
  string in its typed result. Workers cannot introduce arbitrary trusted
  filesystem references.
- Writer results report intent and observations; the backend computes the
  authoritative Git diff.
- Workers may report a typed escalation claim but cannot select a model,
  frontier tier, transition, or persisted state change.
- Every request validates before dispatch.
- Every response validates completely before result application.
- Dispatch IDs must match exactly.

### OpenCode dispatch and correction

The locked OpenCode 1.18.10 SDK supports child `session.create()` with a parent
session and agent, `session.prompt()` with an agent and output format,
`json_schema` output with a retry count, `AssistantMessage.structured`, and
structured-output failure reporting.

Implementation:

- Add a direct runtime dependency on `@opencode-ai/sdk` 1.18.10.
- Construct the v2 client from the plugin-provided `serverUrl`.
- Create a child session per dispatch and store its session ID before prompting.
- Use JSON Schema output with host `retryCount: 0`.
- Validate `message.structured` locally with the canonical Zod schema.
- On host structured-output failure or local schema failure, allow one explicit
  correction prompt in the same child session, with the same dispatch ID and
  exact validation errors.
- A second failure records `worker-invalid-output` and consumes the dispatch
  failure budget; no partial result is applied.
- Persist sanitized raw host parts when available plus the parsed candidate
  under `specops-worker-output/<dispatchId>/<attempt>.json`, with bounded size
  and hashes referenced from state.

### Permissions

Direct child dispatch must preserve or strengthen native task restrictions:

- `assessment`, `planning`, `verification`, reviews, adjudication, and frontier
  analysis are read-only.
- Only `implementation` and `repair` may edit or execute mutation-capable
  commands.
- Workers cannot invoke primary-only SpecOps tools, spawn arbitrary nested
  tasks, or write outside permitted repository scope.
- Validation commands run through the backend registry, not through verifier
  shell access.

### Controller-facing tools

Normal orchestration exposes only:

```text
specops_start
specops_advance
specops_respond
specops_status
specops_cancel
```

Behavior:

- `specops_start`: accepts immutable goal, requested tier, and mode; internally
  assesses and creates the run atomically.
- `specops_advance`: folds deterministic internal transitions and executes at
  most one bounded stage episode or independent batch; returns progress, a
  typed pause, or a terminal result.
- `specops_respond`: consumes an exact response for one pending pause.
- `specops_status`: returns diagnostic state and trace summaries.
- `specops_cancel`: records a safe terminal cancellation.

`specops_archive` remains a separate post-run lifecycle operation because
archival is not normal progression. It creates a typed confirmation pause
consumed by `specops_respond`.

Keep `specops_onboard` and `specops_doctor` as administrative tools. Remove
controller access to next-action payloads, completion, recovery, context,
validation, finalization, individual question/checkpoint handling, archive
confirmation, and generic OpenSpec invocation.

### Capability routing

The scheduler reasons only about capabilities:

```text
assessment
planning
implementation
verification
security-review
data-review
performance-review
migration-review
compliance-judgment
correctness-judgment
adjudication
frontier
```

A separate registry maps `(capability, purpose)` to configured agents and
models.

Each specialist dispatch requires a persisted trigger:

```ts
type DispatchTrigger =
  | { type: "assessment-risk"; facet: RiskFacet; evidenceIds: string[] }
  | { type: "diff-facet"; facet: RiskFacet; paths: string[] }
  | { type: "finding"; findingIds: string[] }
  | { type: "policy"; policyRuleId: string };
```

No agent is dispatched merely because it exists.

Independent consultations or reviews can be issued as one atomic dispatch
batch and run with `Promise.allSettled`. Each response is individually
validated, but stage aggregation waits for the whole already-issued batch. Once
a batch reports a blocking finding, no additional ordinary review batch is
issued for that epoch.

### Verification, findings, and repairs

The base verifier returns registered command evidence,
requirement-by-requirement results, normalized candidate findings, correctness
verdict, compliance verdict when applicable, and assurance summary.

Correctness and compliance agents remain available but become conditional
independent judges for Full/high-risk work, configured policy, or conflicting
evidence. The review ledger becomes a deterministic state projection. The
refuter becomes a one-time adjudication capability for disputed, unsupported,
or conflicting blockers.

```ts
type Finding = {
  id: string;
  fingerprint: string;
  severity: "advisory" | "blocking";
  facet: RiskFacet;
  summary: string;
  evidence: EvidenceRef[];
  affectedPaths: string[];
  suggestedRepair?: string;
  sourceDispatchIds: string[];
  firstSeenEpoch: number;
  lastSeenEpoch: number;
  status:
    | "open"
    | "queued"
    | "fixed"
    | "recurring"
    | "refuted"
    | "dismissed"
    | "escalated";
  resolution?: FindingResolution;
};
```

Lifecycle:

```text
verify/review batch
→ validate evidence
→ normalize and fingerprint
→ merge duplicates
→ no blocker: complete
→ blocker: create repair task immediately
→ repair changes implementation
→ increment epoch and invalidate dependent evidence
→ verify new epoch
→ mark absent/passing findings fixed
→ mark repeated fingerprints recurring
→ one adjudication for a disputed or repeatedly recurring blocker
→ repair, explicit user decision, or blocked terminal outcome
```

Fingerprints use facet, stable rule/requirement key when available, normalized
summary, sorted affected paths, and evidence locators. Repair tasks contain
exact finding IDs, target paths, repair criteria, and source epoch.

### Implementation epochs and invalidation

```ts
type RepositoryBinding = {
  implementationEpoch: number;
  diffHash: string;
  policyRevision: number;
  artifactVersions: Record<string, number>;
  verificationRunId?: string;
};
```

- Epoch 0 is the baseline.
- An accepted Build or Repair result increments the epoch only if the backend
  observes a changed diff.
- An unchanged Repair is a failed repair, not completion.
- Implementation-bound command, verification, and review evidence is
  invalidated on a new epoch.
- Assessment and Plan evidence remains valid unless its own dependencies
  changed.
- A planning repair increments affected artifact versions and invalidates Build
  and Verify inputs.
- Review eligibility requires the current implementation epoch, policy
  revision, artifact versions, and verification run ID.
- The same reviewer and trigger cannot run twice in an unchanged epoch.

### Budgets

Budgets are maxima, not targets:

| Budget | Lean | Standard | Full |
|---|---:|---:|---:|
| Primary dispatches | 6 | 10 | 14 |
| Specialist consultations | 0 | 4 | 8 |
| Review episodes | 0 | 4 | 8 |
| Repair cycles | 1 | 2 | 3 |
| Repeated finding fingerprints | 1 | 2 | 2 |
| Frontier escalations | 0 | 1 | 2 |
| Unchanged-epoch redispatches | 0 | 0 | 0 |
| Schema corrections per dispatch | 1 | 1 | 1 |

Every consumption appends:

```ts
type BudgetEvent = {
  sequence: number;
  kind: BudgetKind;
  amount: number;
  limit: number;
  reasonCode: ReasonCode;
  triggerIds: string[];
  dispatchId?: string;
  implementationEpoch: number;
  at: string;
};
```

Counters are derived from events. Exhaustion produces a typed pause, escalation,
or blocked outcome according to policy; it is never interpreted as successful
completion.

### Pause and checkpoint model

Interactive pauses occur only for approval of the completed Plan before
repository mutation, genuine missing user input, an explicit material scope or
risk decision, and archive confirmation.

There are no per-artifact or routine Build/Verify checkpoints. Automatic mode
records an automatic Plan approval transition. Both modes use the same
transition engine.

Each pause has a deterministic subject/epoch identity and is consumed once.
`specops_respond` accepts OpenCode's native answer arrays without controller
restructuring and resolves them against the persisted pause schema.

### Persistence and transaction model

`RunStateV7` becomes the sole authoritative workflow record:

```ts
type RunStateV7 = {
  version: 7;
  revision: number;
  runId: string;
  startRequestId: string;
  input: SemanticInput;
  identity: DerivedIdentity;
  mode: RunMode;
  tier: Tier;
  stage: RunStage;
  stageAttempt: number;
  policyRevision: number;
  implementationEpoch: number;
  assessment: Assessment;
  plan?: PlanState;
  transitions: TransitionEvent[];
  dispatches: Record<string, DispatchRecord>;
  episodes: EpisodeRecord[];
  triggers: DispatchTrigger[];
  artifacts: ArtifactRecord[];
  evidence: EvidenceRecord[];
  findings: Finding[];
  repairTasks: RepairTask[];
  pauses: PauseRecord[];
  budgetEvents: BudgetEvent[];
  status: RunStatus;
  outcome?: RunOutcome;
  archiveOperation?: ArchiveOperation;
  createdAt: string;
  updatedAt: string;
};
```

- Validate the complete state on every read and before commit.
- Replace `withRunLock()` implicit publication with `begin`, `commit`, and
  `abort`.
- Apply accepted worker results as one atomic transaction.
- Store rejected raw attempts in an immutable audit location, then atomically
  append only the corresponding failure/correction event.
- Fold context, evidence, artifact status, frontier state, and progress into the
  canonical state; progress files may remain derived caches only.
- Preserve an untruncated transition trace. Small budgets bound its size.
- Keep terminal receipts derived from the canonical state.

### Dispatch and crash recovery

Dispatch lifecycle:

```text
prepared → executing → accepted
                    ↘ failed
                    ↘ cancelled
```

Persist the child session ID and deterministic prompt message ID before
external execution.

Recovery rules:

- Before child creation: resume the prepared dispatch.
- Child created, prompt status unknown: query by session/message identity; do
  not send a second prompt blindly.
- Prompt running: wait, resume, or abort according to typed SDK status.
- Valid response exists: submit through the same internal acceptance path.
- Writer crashed after partial repository mutation: inspect the durable child
  response and actual diff under writer guards. If no valid response exists,
  record failure and schedule a bounded same-capability recovery against the
  observed diff; never infer success.
- Repeated submission of the same accepted response returns the existing
  receipt only when hashes match; a different response for an accepted dispatch
  is rejected as a conflict.

### Error model

Use closed error codes:

```text
invalid-input
invalid-change-id
identifier-exhausted
assessment-invalid
worker-invalid-output
worker-unavailable
dispatch-conflict
evidence-invalid
budget-exhausted
openspec-failed
integrity-violation
unsupported-state
cancelled
```

No error string, summary, or regular expression may directly choose a
transition.

## 9. Risks and rejected alternatives

### Retain the artifact-driven scheduler

Rejected. It turns deliverable structure into orchestration structure, creates
unnecessary dispatch boundaries, and is the source of much of `nextAction()`
complexity. Artifacts remain useful outputs, but not stages.

### Strengthen controller prompts

Rejected. Commit history shows repeated prompt hardening around markers,
retries, and feedback loops. Prompts cannot make schema translation,
idempotency, or state mutation deterministic.

### Keep HTML control markers

Rejected. They mix prose with control data, can be echoed accidentally, are
difficult to version, and cannot express mutually exclusive states safely.

### Put more decisions in the model controller

Rejected. The controller should start, advance, present a typed pause, and
report results. It must not choose transitions, repair internal identifiers, map
schemas, select frontier models, or interpret errors.

### Run every specialist or review by default

Rejected. It makes ordinary work slower than OpenCode Plan/Build and provides
no evidence that the extra reviews are relevant. Specialists remain available
through deterministic triggers.

### Retain legacy and new engines

Rejected. Two engines would duplicate state, schemas, recovery, tests, and
documentation, recreating the problem v0.17 is meant to remove. The only
supported runtime is v7; v6 data is quarantined unchanged.

### Use JSON without correction and failure semantics

Rejected. Native structured output improves enforcement but does not guarantee
valid model output. Local validation, one bounded correction, raw-attempt
persistence, and a typed terminal failure are mandatory.

### Allow arbitrary model-selected escalation

Rejected. A worker may report an evidence-bound concern. TypeScript policy
decides whether it qualifies for another capability, a frontier model, a pause,
or a blocked outcome.

### Rename Lean to Simple

Rejected. The existing name is understandable, externally visible, and
unrelated to the reliability problems. Preserve `Lean`, `Standard`, and `Full`.

### Keep correctness, compliance, and refuter as mandatory dispatches

Rejected. Correctness and applicable compliance become required fields of base
verification. Independent judges remain conditional. The ledger is
deterministic; refutation becomes a bounded adjudication episode.

### Checkpoint every artifact

Rejected. It encourages artifact-stage coupling and repeated feedback loops.
Pause after the completed Plan, for genuine missing input/material decisions,
and before archive.

### Risk: direct SDK runtime changes

Mitigation:

- Pin and test OpenCode 1.18.10.
- Check the SDK contract during packed-install CI.
- Fail closed when the runtime lacks required session or structured-output
  support.
- Do not restore controller translation as fallback.

### Risk: oversized structured results

Mitigation:

- Keep bounded Markdown fields in capability-specific results.
- Persist raw attempts outside the main state with hashes.
- Reject oversized results with one correction opportunity.
- Do not accept arbitrary worker-selected file references.

### Risk: staging OpenSpec outside the canonical project

Mitigation:

- Give the OpenSpec adapter an explicit project root.
- Construct staging with the same configuration and read-only spec inputs.
- Add parity tests comparing staged and direct OpenSpec output.
- Publish only through same-filesystem rename.
