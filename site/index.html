SPECOPS

Evidence-bound planning, review, and repair for OpenCode

opencode plugin @jrpbuilds/specops -g

Requires OpenCode 1.16.2+ and Node.js 20.19+

Why SpecOps

Broad agent toolkits can add memory, skills, integrations, and optional SDD conventions. SpecOps has a narrower job: enforce one inspect, plan, implement, review, repair, and completion lifecycle inside OpenCode. Models do the reasoning; deterministic TypeScript decides what may run, what evidence counts, and whether the change is complete.

What the workflow enforces

Decision Enforced by
Scope, risk, and required specialists Assessment policy and the observed implementation diff
Next action One scheduler with at most one active dispatch
Planning and design artifacts Strict contracts, controller validation, and atomic writes
Validation results Registered commands bound to the current diff and policy
Review findings Independent submissions with evidence and acceptance criteria
Finding disposition A refuter that must sustain or dismiss every source finding
Repair work Controller-built tasks grouped by planning, design, or code
Frontier assistance Opt-in evidence checks, tier policy, and hard budgets
Completion Fresh evidence, valid artifacts, and verified repair tasks

Prompts, models, and prose cannot mark work complete. The receipt is created only after the current diff passes every required artifact, evidence, review, repair, and OpenSpec gate.

Scope Tiers

SpecOps chooses the smallest safe route from repository evidence, risk, and uncertainty. Known risk sets the initial floor; newly discovered risk or an implementation that outgrows its estimate raises the tier before final assurance.

Lean L

Small, bounded changes with no requirement, public-contract, or identified risk expansion.

  • Four calls on the successful normal path.
  • Assessor, compact plan, implementation, and assurance.
  • Verification, correctness judgment, and review ledger remain controller-validated completion gates.

Standard S

Features, behavioral changes, bounded refactors, compatible public contracts, and detected risk that does not require Full.

  • One validated planning bundle contains the proposal, normative specifications, and implementation tasks.
  • Risk facets select focused consultations and fresh independent post-implementation reviews.
  • Every blocking finding enters the same evidence-bound repair policy.

Full F

Broad changes, migrations, infrastructure work, breaking contracts, configured high-risk facets, or low requirements/design confidence.

  • Requirements are persisted before design begins.
  • An independent designer produces the technical design from those requirements.
  • Tasks are refined only after the proposal, specifications, and design are valid.

Workflow

Interactive, automatic, and CLI runs share one scheduler and one persisted state. Each stage must satisfy its contract before the next action can be issued.

  1. L S F

    Assessment

    Repository evidence sets scope, risk facets, required capabilities, validations, and review policy.

  2. L

    Compact plan

    Lean keeps bounded work to a four-call normal path without removing assurance or receipt gates.

  3. S F

    Exploration and planning bundle

    Standard and Full persist repository-grounded exploration, proposals, and normative specifications.

  4. F

    Independent design

    Full adds an independent design stage produced from persisted requirements before tasks are refined.

  5. F

    Task refinement

    Tasks are refined from the persisted proposal, specifications, and design. Standard tasks are bundled.

  6. S F

    Specialist consultations

    Specialist consultations are selected during planning based on detected risk facets.

  7. L S F

    Implementation

    Only implementer and repairer agents mutate code; writer guards protect the baseline and controller-owned artifacts.

  8. L S F

    Registered verification

    Declared project commands run without a shell and record results bound to the current implementation diff and policy.

  9. S F

    Independent judgments

    Correctness and compliance judges return strict verdicts plus evidence-backed findings and acceptance criteria.

  10. S F

    Cross-cutting risk scan

    A general reviewer finds cross-cutting risk and can add a specialist route, but cannot satisfy that specialist review.

  11. S F

    Independent specialist reviews

    Each selected risk facet receives a fresh review bound to the exact diff, policy, inputs, and independent dispatch.

  12. S F

    Refutation ledger

    The refuter must sustain or dismiss every current source finding exactly once, with duplicate and unsupported findings accounted for.

  13. S F

    Adaptive frontier adjudication

    When adaptive mode is enabled, verified blockers can spend a bounded low-tier call; high-tier models are reserved for critical or repeated evidence.

  14. L S F

    Repair and re-verification

    The controller groups findings into scoped repair tasks. Fresh assurance—not the repairer—decides whether each task is verified.

  15. L S F

    Completion receipt

    Completion requires current command evidence, valid artifacts, fully accounted findings, and no unresolved repair task.

Key Capabilities

Concrete guarantees enforced across the complete change lifecycle.

  • Evidence-led scope

    Lean, Standard, and Full routes selected from repository evidence, risk, uncertainty, and the actual changed paths.

  • One scheduler

    Interactive, automatic, and CLI entrypoints share the same ordered actions, budgets, persistence, and completion policy.

  • Validated OpenSpec planning

    Proposals, normative specs, design, and tasks are contract-checked before controller-owned atomic persistence.

  • Risk-specific specialists

    Ten risk facets can add focused planning consultation and a distinct independent post-implementation review.

  • Safe command evidence

    Registered executable and argument arrays run without a shell, with confined paths, timeouts, bounded output, and immutable hashes.

  • Exact-diff provenance

    Artifacts, commands, judgments, and review submissions are bound to the implementation diff and policy they evaluated.

  • Bounded material questions

    Workers may pause for a genuinely unresolved user decision; answers are hashed into provenance and stale dependent work.

  • Evidence-backed findings

    Judges and reviewers submit severity, repair mode, repository or command evidence, and observable acceptance criteria.

  • Complete refutation

    Every current source finding must be sustained or dismissed exactly once before the review ledger is accepted.

  • Controller-built repair tasks

    Compatible findings are grouped by planning, design, or implementation with exact evidence and acceptance criteria.

  • Fresh repair assurance

    No-op code repairs fail, downstream assurance is invalidated, and a fresh ledger must stop sustaining the finding.

  • Adaptive low/high frontier

    Optional, evidence-gated escalation spends bounded low/high model calls and returns advice to a fresh originating dispatch.

  • Native model mapping

    Choose a configured OpenCode model and variant for every controller, workflow, review, frontier, repair, and specialist role.

  • Completion receipts

    Machine-readable receipts retain baseline, diff, requirements, dispatches, artifacts, findings, repairs, and frontier history.

Commands

SpecOps registers the same controllers and protocol tools for visible OpenCode sessions and non-interactive automation.

SpecOps public command reference
Command Purpose Runtime target
/specops-auto Run visible deterministic SpecOps workflow primary agent specops-auto-controller
/specops Run deterministic SpecOps workflow with checkpoints primary agent specops-interactive-controller
/specops-onboard Install final SpecOps OpenSpec assets protocol tool specops_onboard
/specops-status Show final SpecOps run status protocol tool specops_get_status
/specops-doctor Diagnose final SpecOps installation protocol tool specops_doctor

Map models in OpenCode

Press Ctrl + P and select SpecOps: Configure agent models. Choose any model already configured in OpenCode—and an exposed variant—for each of the 24 controller and worker roles. For dependable remediation, assign a strong coding model to specops-repairer; adaptive escalation uses the separate specops-frontier-low and specops-frontier-high mappings.

Prerequisites

  • OpenCode 1.16.2 or newer
  • Node.js 20.19 or newer
  • A Git repository with at least one baseline commit
  • OpenSpec assets installed by SpecOps (/specops-onboard)

CLI adapter

The same automatic workflow is available without opening the TUI through OpenCode's supported CLI adapter: 

opencode run --command specops-auto --dir /path/to/project \
  "add a health endpoint with tests"

Use --format json for raw NDJSON events suitable for CI. Do not add OpenCode's unrelated --auto permission flag.

Get Started

Install the plugin, map your models, onboard the repository, and run an evidence-bound change.

opencode plugin @jrpbuilds/specops -g

Restart OpenCode, then use Ctrl + P → SpecOps: Configure agent models. Onboard and verify the project when the mappings are ready: 

/specops-onboard
/specops-doctor

Adaptive frontier routing is opt-in. Set frontier.mode to adaptive in .opencode/specops.json when you want evidence-gated low/high escalation.
